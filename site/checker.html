The Zizkian logic checker

Run from the repository root with SWI-Prolog installed:

swipl -q -s src/check.pl -- examples/hypothesis.json
swipl -q -s tests/test_zizkian.pl -g run_tests -t halt
swipl -q -s proof/refutable.pl

The checker reads JSON as data. It does not execute supplied Prolog, call models, fetch sources, change files or send messages. No dependencies were installed. Its public predicates are zizkian:audit/2 and zizkian:audit_file/2.

?- use_module('src/zizkian.pl').
?- audit_file('examples/defeated.json', Report).

audit/2 accepts a ground dict with atom values and grounded dict tags, as produced by json_read_dict/3 with value_string_as(atom), default_tag(data). Do not pass variables to mean unknown. Use hypothesis, untested and unasked. Missing, blank, mistyped and unrecognized fields are invalid; there are no silent defaults. Evidence and reading IDs must be unique, and references must resolve.

Exit Status Meaning
0 pass Record satisfies these encoded rules; warnings may remain
1 blocked Valid input violates one or more reasoning rules
2 invalid Repair input, schema, references or invocation

Passing verdicts are no_finding, ready_for_test and ready_for_decision. Every violation contains rule, target and message. All detected violations are returned, rather than stopping at the first one. Warnings preserve explicitly untested alternatives and falsifiers.

Record contract

All listed fields are required. See the complete examples rather than inventing an incomplete record. schema/2 in zizkian.pl is the executable schema.

Object Fields
Case id, mode, coaching_invited, brief, desired_result, owner, lenses, ordinary, return_cut, evidence, readings, outcome
Ordinary alternative claim, check, status (untested or checked), evidence IDs
Return cut observer, statement, defeater, status (hypothesis or no_finding)
Evidence item id, statement, source, kind (observation, participant_rejection or attention_weight)
Reading id, claim, status (hypothesis, supported or withdrawn), response (unasked, accepted or rejected), support IDs, counterevidence IDs, defeat_test
Defeat test method, defeating observation, status (untested, survived or defeated), evidence IDs
Outcome kind (retain_brief, test or change), action, reason, reading_ids, stop_rule

supported is a declared epistemic status, not a conclusion generated by this program. Likewise, survived means the submitted record declares that the test did not defeat the reading; it does not mean the reading is universally true.

Consulting uses 1 to 3 distinct business lenses, optionally including veil_piercer. Coaching uses one personal lens or veil_piercer, requires invitation and an accepted framing for a selected next step. Rejection cannot support any active reading, and a rejected framing cannot drive the participant’s next step.

An active supported reading needs observation evidence and no unresolved declared counterevidence. The same item cannot count as support and counterevidence. Defeated readings must be withdrawn. Observed test results and checked ordinary alternatives require an observation reference. A change requires a checked ordinary alternative and supported selected readings. A test may select a hypothesis. Closure uses no selected reading and permits withdrawal.

Runnable examples

Every example is fictional, including its evidence and participant statements.

Input Expected status Why
hypothesis.json pass / ready_for_test, warnings A test is proposed without claiming an observed result
supported.json pass / ready_for_decision Declared support, alternative check and test record are present
defeated.json blocked Reading remains active after its defeating observation
withdrawn.json pass / no_finding Withdrawal permits closure
no-finding.json pass / no_finding An ordinary answer needs no dramatic reading
rejection-trap.json blocked Rejection is used as evidence and the refused framing drives a step

Scope and limitations

This checks the structure and declared relationships of a reasoning record. It cannot judge whether a sentence actually supports another sentence, a source exists, a test was honestly performed, consent was real, or a falsifier is strong. Mislabelled rejection as observation can evade a type check. Arbitrary prose can fill every required field. Human evidence review remains necessary.

Negation-as-failure is used only after input validation: missing support in the record blocks a supported claim. It does not prove that no support exists in the world. No attention weights, confidence score or voting arithmetic are applied. Changing a lens cannot change the supplied evidence.

The checker is available for manual use. It is not automatically connected to a dispatcher. See the field guide.

The implementation uses SWI-Prolog’s documented JSON dict interface and PlUnit.

Treat structural passage as a review aid [1 SPECULATIVE | no outcome benchmark]. If that use is wrong, the first signal is a misleading record passing despite a human reviewer finding unsupported conclusions or an unusable defeating test.
